# Samewhere

An initial browser prototype of a spatial puzzle game. Seven logical rooms, four balls, and doorways that can be connected to one another. Built with Three.js, TypeScript, and Vite; geometry and sound are generated procedurally, and textures are loaded from local files. No external models or fonts are used.

The visual style follows the supplied Backrooms references: yellow wallpaper with a small repeating pattern, beige carpet, a suspended ceiling with a 65 × 65 cm grid, and rectangular fluorescent panels. Geometry stays simple, without guide lines on walls or pedestals. Nearby rooms have no fog or color filter. Distant rooms gradually darken between 48 and 68 m, retaining their hues until they disappear. Lighting creates contrast and draws warmth from the environment itself; the menu slightly blurs the scene.

The wallpaper, carpet, cast-concrete pedestal, and mineral ceiling-tile textures were created for Samewhere with the built-in `image_gen` tool; the thin T-bar ceiling grid is added in code. The exact generation prompts and material scales are recorded in the [material sources](public/materials/sources.json). The game does not contact external services.

## Getting started

Requires Node.js 22.12+ and a desktop browser with WebGL 2.

```sh
npm install
npm run dev
```

Open the Vite URL (usually http://127.0.0.1:5173/) and select `NEW GAME`. If an embedded preview blocks pointer lock, open the URL in a separate Chrome, Edge, or Firefox tab.

```sh
npm test          # Rules, transforms, collisions, and undo
npm run build    # TypeScript checks and a production build in dist/
npm run preview  # Preview the production build locally
npm run test:browser # Browser acceptance tests
npm run profile   # Measure fast turns in Chrome; Vite must be running
npm run profile:pacing # Headed Chrome, GPU measurements, and frame presentation traces
npm run profile:interactions # Compare ball interaction and walking workloads
npm run profile:lighting # GPU/CPU measurements with and without light transfer in matching scenes
npm run profile:hub # First opening into H and an actual transition to the hub
```

Browser tests use the installed Google Chrome through Playwright and start Vite automatically if no server is running. Screenshots are saved in `test-results/`. To use another browser, change `channel` in `playwright.config.ts`.

Panel lighting, one bounce from floors and walls, and illumination through every possible doorway connection are calculated in Node.js at build time. The browser loads the prepared binary and initializes the GPU; there is no CPU lighting bake when the game starts. Vite automatically regenerates the file when the level, lighting, algorithm, or its dependencies change. During local development, these changes wait for the new file and fully reload the game. Unchanged data comes from `node_modules/.cache/samewhere-lighting/`; no separate bake command is needed.

`npm run dev` uses a fast draft lighting bake; `npm run build` uses the full-precision bake. They have separate files and caches. Check subtle bands and shadow boundaries with `npm run build` and `npm run preview`.

Baked direct lighting from local panels and bounced lighting store the derivative of irradiance with respect to normal tilt, including bounce through portals. It is calculated from the same source integral as brightness, clipped to the surface horizon. The shader uses a linear approximation to respond to the normal map; zero normal strength preserves the original brightness. Microshadows are not modeled. Local maps contain three RGBA planes (brightness, bounce derivative, and direct-light derivative); portal bounce maps contain two. The planes are packed into one texture to avoid increasing the GPU sampler count in the hub with its seven sources. Cached direct lighting from neighboring rooms currently uses the geometric normal.

## GitHub Pages

Publishing is manual through [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml). Push the workflow to the default branch, then:

1. In the repository, open **Settings → Pages → Build and deployment** and select **GitHub Actions** as the source.
2. Open **Actions → Deploy to GitHub Pages → Run workflow**, select `main`, and start the workflow.
3. Once deployment finishes, open https://art-bazhin.github.io/samewhere/.

The workflow installs locked dependencies with `npm ci`, runs the production build with full-precision lighting, includes `COPYRIGHT`, and publishes only `dist/`. It caches lighting using the bake's own dependency revision, including the Node.js version, so an unchanged bake can be reused. Generated lighting data stays out of Git. Ordinary pushes do not trigger a build or deployment.

Vite uses a relative base (`./`), and runtime material URLs respect `import.meta.env.BASE_URL`, allowing the game to run under `/samewhere/` without loading assets from the domain root. Music and lighting asset URLs are generated by Vite. See the [Vite base-path documentation](https://vite.dev/guide/build#public-base-path) and [GitHub Pages workflow documentation](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

| WASD, arrow keys | Move |
| Mouse | Look around |
| Left-click a socket | Pick up a ball / place the selected ball |
| 1 / 2 | Select red / blue |
| Mouse wheel | Switch between ball colors currently held |
| Z | Undo a pickup, placement, or transition (only with `?dev=1`) |
| R | Restart (only with `?dev=1`) |
| Esc | Open the pause menu; resume with Esc only in fullscreen; close the controls dialog |
| F | Toggle fullscreen |
| F3 | Diagnostics, FPS, and resources |
| F4 | Six-second frame-pacing test: the camera turns automatically; press again to stop |
| T | Toggle textures to inspect shadows |
| Tab | Debug room travel: hub H → A → B → C → D → E → F → hub; after a reset, the first transition goes to the hub again |
| 0 / Num0 | Prepare the gallery test: square room with four symbols, all balls in hand; Z undoes the jump |
| 9 / Num9 | Last gallery room before the white space, facing EXIT; balls placed, route active; Z undoes the jump |
| M | Toggle sound |

Opening and closing the menu fades its text and changes the background blur over half a second. A closing menu stops accepting input immediately.

In windowed mode, resume using the `RESUME GAME` button. In fullscreen, the game requests Keyboard Lock for `Esc` only: in supporting browsers, a short press toggles pause, while holding the key preserves the system fullscreen-exit behavior. The key is unlocked when fullscreen ends. If the API is unavailable or the browser rejects the request, normal browser behavior is preserved.

Approach a pedestal and look down at a ball or socket: the crosshair dot grows slightly when interaction is available. Interaction range is 2.25 m. Every socket can be reached from one side of the pedestal. An occupied socket always returns its ball, without automatically swapping it.

During normal play, the only interface elements are a small crosshair dot and the balls in hand at the bottom of the screen: one colored circle per ball, with the selected color slightly larger and all circle centers on the same horizontal line. An empty inventory disappears completely. Keys 1/2 select only an available color; placing the last ball of the selected color automatically selects the remaining color. There are no panels, numerical counters, or text hints during play. The interface is in English. The menu has no backing panel and contains `NEW GAME`, `CONTROLS`, and, once a game has started, `RESUME GAME`. Above the items, the `samewhere.` logo is enlarged with `scale(3)` and aligned to their left edge; it ignores pointer events and cannot be selected. Resuming preserves the current state. If a game is already in progress or has been restored from a save, `NEW GAME` shows a progress-loss warning styled like `CONTROLS`: `CANCEL`, `Esc`, or a click on the backdrop cancels; only `CONTINUE` resets the world, history, and music layers. Without a current game, play starts immediately. `CONTROLS` opens a dialog with a controls table, no heading, and a centered `BACK` button; keyboard and wheel color selection share one row. Close it with `BACK`, `Esc`, or a click outside on the backdrop. Focus outlines appear only during `Tab` navigation. The player starts between the square pedestal and the wall in A, looking horizontally straight at the wall.

The game automatically saves to `localStorage`: world state, player position and view direction, selected color, undo history, symbol and gallery progress, unlocked music layers, and mute state. Actions and transitions are saved immediately; movement is saved once per second. Pausing or leaving the page updates only an existing save key: manually deleting a save does not recreate it on reload. After a reload, `RESUME GAME` continues the saved game; `NEW GAME` and `PLAY AGAIN` replace it with a new one. Corrupt or incompatible saves are ignored. If storage is unavailable, the game continues without saving.

Until graphics and music finish loading for the first time, an opaque black cover hides level preparation. `LOADING` and a thin progress bar appear in the center. The bar tracks actual material, lighting-data, and music downloads, decoding, shader compilation, and GPU preparation. Uncompressed files with a known length report received bytes; other operations count when complete. This is the fraction of work completed, not an estimate of time remaining; 100% is reached only when graphics and every music track are ready. Once preparation finishes, the cover and label fade out over 0.6 seconds, revealing the menu over a blurred background; the menu does not accept input until the animation ends. The loading screen is styled before the game JavaScript starts; an error reveals a message in the menu.

Debug keys `F3`, `F4`, `T`, fast travel with `Tab`, `0 / Num0`, and `9 / Num9`, undo with `Z`, and restart with `R` are available only with the URL parameter `?dev=1`. In this mode, FPS also appears in the top-right corner; without the parameter, or with any other value, the counter is hidden and all these commands are disabled.

Music consists of six synchronized loops, `music/SAMEWHERE-001.mp3`–`006.mp3`. Selecting `NEW GAME` starts all tracks simultaneously: `001` has an additional 10 dB attenuation, and the others start silent. Layers fade in over 15 seconds: `002` on the first entry into B, `003` into D, `004` into hub G, `005` when returning to A after following the symbol chain, and `006` after completing the final ball pattern in A. Unlocked layers persist through backtracking and undo. `R` returns the music to layer `001` while preserving the shared loop phase; `M` smoothly mutes or unmutes all sound. Both edges of each loop have a 5 ms fade. Opening the menu fades all audio out over 500 ms, then suspends the shared audio context, pausing loops and fades. Resuming preserves phase and synchronization and fades audio back in over 500 ms. After a page reload, previously unlocked layers start immediately at their target volume; the 15-second fade applies only to newly unlocked layers during play. Entering the white space fades tracks `001`–`004` and `006` out from their current levels over 12 seconds; `005` continues playing. `PLAY AGAIN` restores the initial music layers.

F3 opens diagnostics: FPS, frame time, p95 intervals between game-loop calls, CPU time, long frames, and the GPU measurement queue. FPS counts JavaScript calls and does not itself guarantee that the browser presented every frame on the display. GPU time is measured asynchronously through `EXT_disjoint_timer_query_webgl2`, once every four frames, with at most eight pending queries. A dash is shown if the extension is unavailable. The game loop never waits for GPU results or calls `gl.finish()`. Returning from a background tab resets the CPU measurement window. Mouse input requests raw movement without system acceleration; if the browser returns `NotSupportedError`, standard pointer lock is used.

F4 turns the view through a full circle at a steady rate over six seconds, then restores the original direction. Position and balls are preserved; walking and interaction are paused during the test. This helps distinguish input issues from rendering or frame-presentation issues. Pressing F4 again, Esc, resetting, or undoing stops the test.

Mouse look uses `pointerrawupdate` with individual samples from `getCoalescedEvents()`, falling back to `mousemove` when unsupported. Only one event stream is active at a time. By default, all received movement is applied before the next frame, without an additional buffer. Sensitivity is 0.002 radians per movement unit.

There is no smoothing, interpolation, or inertia after input stops. Pausing, resetting, undoing, and F4 clear accumulated movement. After a portal transition, remaining relative mouse movement is applied to the transformed view direction.

## Rules

A pedestal's shape matches the room it controls. Every pedestal shows the shared state of that room, wherever the player is. In A–D, sockets correspond to polygon walls; in E–G, they correspond to corridor ends. The first symbol is in the hub.

| Room | Pedestals |
| --- | --- |
| A — square | A and B |
| B — pentagon | C |
| C — hexagon | D |
| D — triangle | A and E |
| E — Y: three equal corridors | B and F |
| F — +: four equal corridors | G |
| G — H: hub, two parallel corridors joined by a crossbar | All seven: A, B, C, D, E, F, and G |

Two placed balls of the same color connect the corresponding walls. If either ball is in the inventory, both doorways of that pair disappear and become ordinary walls. Connections can link different rooms or different walls of the same room.

The player starts in A with an empty inventory. Both red balls are placed on pentagonal pedestal B, connecting B0–B2. Both blue balls are on hexagonal pedestal C, accessible in room B, connecting C0–C3. Every copy of a pedestal shows the same balls. Initially, A and D have no doorways. The player can freely explore and rearrange connections.

A red pentagon is drawn in marker beside the southern doorway of H's left corridor from the start (G3, the fourth socket). Symbols then lead along this chain: G3 → B in red, B2 → D in blue, D1 → A in red. Exit numbering here starts at zero. Any entrance in the destination room is valid. Opening the correct connection is enough: the next symbol appears immediately, without requiring the player to walk through. Symbols remain visible when the doorway is open and after balls are rearranged. Other connections work normally.

Opening the last connection reveals four square-room symbols in the square room simultaneously: red at A0/A2, blue at A1/A3. The stage is completed when the player is in A and all four balls simultaneously occupy the marked sockets on its pedestal, creating two self-connections for the infinite gallery. Controls remain active afterward. Progress is included in undo history and resets with the game; the hub symbol remains.

Completing the gallery configuration immediately reveals green Exit signs along a predetermined route, regardless of the player's position or view. The first is above southern exit A2. The route has 42 transitions from the starting room: straight for 5, left for 5, right for 5, left for 10, then 5 transitions diagonally northeast, and the final 12 straight east into the white space. Along the diagonal, a red doorway on the left alternates with a blue doorway on the right in each successive room. This section can be walked diagonally without changing the view direction. The route never crosses itself or requires turning back through the entrance. Room geometry remains shared, but transitions follow integer gallery coordinates: every recursive view shows the sign for that particular location. Signs remain in place when returning or approaching by another route. Undo restores position and route; resetting removes the gallery. Breaking the two loops hides the signs; completing them again restarts the same route. The last marked doorway leads directly into empty white space, without additional light sources. Over the final seven meters, the image gradually fades to white, reaching full white at the threshold; retreating reduces the effect. Crosshair opacity changes by the same proportion: it disappears completely at the threshold and returns when retreating. Crossing the white doorway disables movement, mouse look, and gameplay keys, and hides the crosshair, menu, and cursor. A black `samewhere.` logo fades in over 12 seconds on the white screen while scaling from 1 to 3, staying centered; the text ignores pointer events and cannot be selected. Immediately afterward, `PLAY AGAIN` fades in over one second; the cursor returns and pointer lock is released as its fade begins. `Esc` cannot return to the menu; the button starts a new game.

After D, the E–F–G section becomes accessible. Rooms B–F have no pedestal controlling themselves: moving balls requires controls in other rooms. G cannot be reached while making every transition through A; both initial connections must be changed, and a new staging room prepared. This is checked by enumerating available actions. H is the hub and contains all seven pedestals: A, B, and C stand in the left corridor, spaced 4.2 m apart; D, E, and F are in the right corridor; H's own pedestal is at the center of the crossbar. There is walking space between pedestals and on both sides of the central one. Every copy shows the shared state of its corresponding room and allows connections to be rearranged from the hub.

The new corridors are 3.4 m wide. In Y and +, the ends are 7 m from the center; in H, two 14 m branches are joined by a central crossbar. Doorways appear only at the ends: three in Y, four in +, and four in H. H accounts for the lateral offset of each entrance. Pedestals reproduce the entire room outline, including recesses, with sockets at branch ends. Each pedestal has its own overhead ceiling light.

- `src/white-space.ts` — empty white space with a view back into the gallery.

- `tests/world.test.ts`, `tests/layout.test.ts`, and `tests/browser/game.spec.ts` — automated checks.
- `docs/design-brief.txt` — original design document.

### Views through doorways

Each active doorway is a surface that projectively samples an image of the destination room. The camera for that image is derived from the original camera by transforming between the doorways' coordinate systems and rotating by 180°. Crossing the plane applies exactly the same transformation to the player, preserving lateral offset, pitch, and movement direction.

Walls are **0.30 m** thick. Their inner faces remain at the room's 5 m apothem; a closed wall extends another 0.30 m outward. The transition plane runs through the middle of that thickness, 5.15 m from the center. For an open wall, each scene renders only its own half of the thickness up to the transition plane. Connected halves meet without overlap: the distance from one room's inner wall face to the other's is exactly 30 cm. Doorways have side and top reveals; each half of an open wall is built as one extruded geometry, without an overlaid frame. The doorway floor has a shared neutral threshold whose surface stays continuous for any rotation or room pairing.

Neighbor views are rendered recursively from the deepest level upward. A clipping plane in room coordinates removes geometry in front of the destination doorway. The camera retains a normal perspective projection and depth distribution: approaching a portal does not reduce precision or cause thin surfaces to flicker. Different branches render into separate buffers and appear only on their own doorway surfaces; physical room copies do not intersect or show through walls. The surface immediately in front of the player preserves correct fragment depth separately, preventing the camera's normal near plane from causing a flash before a transition. Within 0.1 mm of the boundary, the doorway projection is stabilized separately, including positions directly on the plane; this removes missing image regions and bands at screen edges.

Visibility range is **48 m**; surfaces begin fading to black in linear color at **28 m**. The fade covers roughly two distant rooms; combined with the increased range, about one more room is visible than at the previous limit. The factor depends on fragment distance from the transformed camera, so movement and portal crossings do not cause abrupt changes. Portal images are not darkened a second time.

Doorways beyond 68 m do not require child renders. The safety limit is 10 transitions, with a budget of **32 passes including the main view**. Short routes through adjacent walls can contain more rooms, so geometric recursion depth exceeds the room count in a straight corridor. A doorway directly at the camera does not consume a recursion level. Neighbors are culled by orientation, screen bounds, and inherited visible region. A child view is also skipped when one opaque wall fully hides its doorway; for open doorways, only the wall's side sections count as occluders. This reduces hidden renders around corners in Y, +, and H. The pool holds at most 31 reusable render targets. At the limit, black is used and concealed by distance fading; scenes and geometry are not recreated during transitions.

Portal pixel density matches the main WebGL canvas, including DPR (capped globally at 1.5). The previous 1200-pixel buffer-width limit is gone. Every recursion level uses the same MSAA sample count as the main image. Textures are read pixel for pixel, without enlargement or blur. Wall and ceiling clipping preserves half a screen pixel of coverage at the doorway plane and accounts for coordinate error: it does not discard an entire fragment when some of its MSAA samples belong to a reveal. Reveal-edge vertices extend another 5 cm only in the image shader, preventing MSAA from mixing in the wall's dark hidden end cap. Texture and lightmap UVs are extrapolated with the surface; physical geometry, collisions, and shadow maps retain the 30 cm thickness. No triangles or render passes are added. Browser checks vary the upper join's angle and subpixel position and separately test side reveals under actual PBR lighting.

On side reveals, local and neighboring direct light use the same GPU doorway calculation, including penumbrae and depth maps. They have separate narrow maps with 2.5 cm spacing, without increasing the density of CPU bounce maps. Coplanar reveals of opposite doorways are not merged into one GPU map. The MSAA coverage extension extrapolates texture coordinates and both direct and indirect lightmap coordinates.

Neighbor buffers contain only the screen region of the corresponding doorway, with a two-pixel margin. The full projection is preserved while the viewport shifts into the cropped texture; the shader accounts for parent and child buffer offsets. Clearing, rendering, and MSAA resolve are limited by `scissor`. Dimensions are allocated in 128-pixel blocks, grow as needed, and persist during walking and turning. One full-screen buffer and five smaller ones are allocated before play; sizes are recalculated on window resize. Depth is not copied after MSAA because only the color texture is needed afterward. Transition matrices are recalculated when connections change; working vectors and recursion lists are reused. Portal depth is written before room materials so surfaces hidden behind doorways do not run expensive PBR shading. HUD hints update only when their text changes.

The main WebGL 2 context is explicitly created with `alpha: false`. HUD panels use an opaque background without `backdrop-filter`, avoiding browser blur of the moving WebGL canvas underneath the interface.

`profile` checks full turns at two resolutions, from the starting position and immediately beside a portal. It measures CPU time, GPU time, filled pixels, pool growth, and buffer allocations after warmup.

`profile:pacing` opens a separate Chrome window with a 1710 × 1107 CSS-pixel canvas at DPR 2. The profiler drives reproducible turns and walking so rendering measurements do not depend on raw-event delivery or automated-window focus; native input is tested separately in browser tests. It compares portals, solid walls, a hidden HUD, and 1× resolution. GPU time is measured asynchronously, and the Chrome trace is saved to `test-results/profiling/chrome-pacing.json`. In automated Chrome, the Fullscreen API flag does not always resize the system window, so canvas dimensions are set explicitly. These measurements do not replace checking presentation on the user's display.

### Materials and lighting

One-meter carpet sections receive stable pseudorandom rotations of 0°, 90°, 180°, or 270°. Color, normals, and roughness rotate together, without blending neighboring tiles. Derivatives of the original UVs preserve correct filtering at a distance. Floors and thresholds use the same pattern; geometry and lightmaps are unchanged.

The yellow wallpaper and beige short-pile carpet are retained. The wallpaper texture is prepared for ordinary seamless repetition: broken motifs were repaired after a half-tile wraparound shift, and the edges match in the PNG itself; the original average color was restored in linear RGB. Large repeating brightness patches were leveled with frequency separation in logarithmic linear RGB, preserving fine lines, ornament, and grain. There is no additional seam or brightness processing during play. Separate linear 1024² normal maps and 512² roughness maps are estimated from the textures during loading. Fine-detail gradients produce restrained relief: 0.65 mm for wallpaper and 3 mm for carpet pile. Color, normals, and roughness use ordinary repetition without mirroring. Relief gradients cross tile boundaries using periodic sampling. Carpet has high roughness and a faint soft fiber sheen. Its highlights and sheen come from the shared room environment; directional sources provide diffuse lighting and dynamic shadows. This keeps sheen continuous when looking obliquely through a doorway, where local point highlights would otherwise stop abruptly. Pedestals and socket bowls use matte concrete with fine pores. The concrete's base color receives 50% of the former beige tint toward #cdbb86; texture detail is preserved as a material multiplier in linear RGB. Socket interiors have the same base color as their pedestal, without extra material darkening. The concrete color map is stored as JPG with an original scale of 0.8 m per tile; separate normal and roughness maps with 0.7 mm relief are estimated during loading. Pedestal sides are unwrapped as one continuous strip around the perimeter, with consistent UV orientation and no mirrored repetition on adjacent faces. A whole number of tiles closes the strip without an extra seam; horizontal scale adjusts slightly to the perimeter, while vertical scale is preserved. Socket textures are projected in pedestal coordinates. Color maps are read in sRGB without desaturation. Physical scales are preserved: wallpaper 1.2 m, carpet 1 m, ceiling 0.65 m. The ceiling uses a typical office mineral-tile texture with fine pores and irregular slits, plus separate normal (1.2 mm relief) and roughness maps. A warm gray-beige T-bar profile, #c9c0ae and 24 mm wide, slightly darker than the tile and without a separate edge stripe, is added to the image during loading; the ceiling fill emission is also modulated by the texture, retaining dark pores. Filtering is linear with mipmaps and up to 8× anisotropy. Play becomes available after materials load and lighting and GPU preparation finish.

The 8 cm balls use a polished-resin `MeshPhysicalMaterial`: a nonmetallic surface with IOR 1.57, roughness 0.137–0.169, and a thin clearcoat. A shared linear 256² map adds barely perceptible variation in polish without color grain. The shared sphere geometry has 64 × 48 segments. A separate sharp PMREM map with 256-pixel faces is captured from the actual center of a placed ball in the starting room after materials and lighting are ready. This includes the shaded socket in the lower reflection; capturing above the pedestal center incorrectly reflected bright concrete and created a light rim underneath. It contains the actual textures, lighting, and geometry of the ceiling, walls, and pedestal; diffuser brightness in the HDR capture is raised for white reflections in the polished resin, while architectural surface contributions are reduced to 28% so walls and the pedestal do not brighten the bottoms of the balls. Only the diffuser above the source ball's pedestal appears in the capture: other panels are hidden during capture because a shared map cannot position their reflections correctly for every socket. Their light sources continue illuminating the room, and all panels become visible again afterward. Balls themselves and screen-space portal images are excluded. Resin and clearcoat highlights come only from the reflection map: directional sources light the balls and cast shadows but do not add duplicate circular highlights over panel reflections. This is one shared approximation of the local environment for all balls; the map is prepared once at startup and is not updated during turns, transitions, or ball rearrangement. No light sources or render passes are added during play.

In an occupied socket, live direct light from each ceiling lamp is checked with an exact ray–sphere intersection. The room shadow map still accounts for other obstacles. For an 8 cm ball, low-resolution back-face depth leaked light near the bowl, while front-face depth caused self-shadowing on the sphere; the exact local check removes the bright concrete stripe without changing the material or adding a dark rim. Baked direct light is additionally occluded by an analytical sphere shadow from the ceiling panel. Penumbra size depends on diffuser size and distance to the ball. Contact shading based on the gap between bowl and sphere attenuates reflected and ambient light at the contact point. Ball presence is passed as one byte per bowl vertex; only the changed socket is updated, without extra render passes or lightmap recalculation. Empty sockets retain an even base tone. The test compares actual bowl pixels with and without the shadow, as well as the first and subsequent frames after picking up or placing a ball.

Pedestals and lights align to a shared **65 × 65 cm** ceiling-tile grid, matching the square pedestal size. Normally, the room origin coincides with a tile center; other centers lie at multiples of 65 cm. In the Y room, pedestals sit exactly on the centerlines of the side corridors: X = ±2.6 m, Z = 2.6 / √3 m. This room's ceiling-grid origin is shifted along Z toward the pedestals so lights remain above them and at tile centers. Loading the configuration rounds pedestal positions to the nearest tile centers while preserving symmetry. The ceiling texture uses the same grid size and offset; the emitting area is 62.6 × 62.6 cm and fills the entire gap between grid profiles, without a strip of ceiling-tile texture around it. Profile width and diffuser size share a common constant.

Every room has one light above each pedestal: two each in A, D, and Y; one each in B, C, and +; seven in H. There are 16 lights in total. One shared position list drives visible panels, sources, baked light, doorway transfer, and reflections. Each panel has its own downward-facing source at its center and a 1024² shadow map. 55% of the static diffuse component is integrated over nine points on the actual 62.6 × 62.6 cm panel; the remaining 45% retain dynamic ball shadows and direct highlights on finishes, while ball highlights come only from reflections of visible panels. The diffuser has a soft tube pattern and prismatic texture. Source intensity is 25. Range is 20 m; in the hub, the four dead-end lights have a 15 m range, while the three central-row lights above pedestals B, E, and G have a 5 m range. Each panel's range is included in direct and bounced light and in doorway transfer. Cutoff is smooth, with inverse-square distance attenuation. Bright areas under panels are distinct from dark corners. Fill light is subdued: HemisphereLight 0.24, AmbientLight 0.016, environment intensity 0.12. When a ball or wall changes visibility, only maps for lights whose cones intersect the changed object are updated. Selecting a ball color or synchronizing again requires no update. Maps are reused across all recursive views. An object change clears and redraws only its conservative projection in the map, including a three-texel margin; other pixels are preserved. Wall projections are clipped to the shadow camera's near plane, and overlapping changes are merged before rendering. Forced full updates and initial preparation retain the full map region. In the ball-interaction check, this is about two thousand pixels instead of several million. After the main render, at most one remaining map for invisible rooms is prepared per frame: work is spread in advance rather than deferred entirely until entering a changed room.

One diffuse bounce is integrated over floor and wall areas: surfaces are split into cells no larger than 62.5 cm, each receiving its own illumination from nine points on ceiling panels. Boundary floor cells are clipped to the actual outline, including angled walls and recesses in complex rooms. Cell portions whose centers lie beyond a wall are retained if their area falls inside the room, leaving no gaps or protruding reflectors along the boundary. Interior rectangular cells keep the original grid. Each cell's visibility is checked separately against walls and actual pedestal silhouettes. Occluding a small part of a reflecting surface therefore no longer removes the contribution of an entire 2.5 m patch or creates a broad band on the wall. Near a cell, its contribution uses the polygon's projected solid angle on the receiving hemisphere; at a distance, quadrature with cosine factors and inverse-square distance is used, with a smooth transition between estimates. Exact doorway dimensions are excluded from reflecting areas; the wall above a doorway still reflects light. Patches remain on the actual wall planes, and corner receivers evaluate the interior irradiance limit, avoiding a dark rim caused by shifting a reflector into the room. Conservative group checks skip individual rays only when the path is guaranteed clear. Walls, complex-room recesses, and pedestal silhouettes are included. The ceiling also receives this bounce: its visible inner face is included in the map at 50 cm spacing, sufficient for soft diffuse lighting. Hidden ceiling/wall overlap extends interior illumination without a black rim. Panels add no direct upward emission. Potential doorway areas do not act as reflecting sources. Direct panel light and colored bounce are packed into one RGBA half-float map per room; seven maps occupy 1.75 MiB. They are prepared once at startup and require one additional texture sample during play, without new passes or sources. This is one bounce using average material colors, not full global-illumination ray tracing.

Walls meet along the exact room outline, with a mitered outer join in plan view; there are no hidden extensions of interior planes beyond corners. Outer faces and hidden end caps occupy no lightmap space. Corner guard texels receive illumination from the actual wall edge, preventing vertical dark bands in the pentagon and hexagon. Each room's half of the threshold and reveals receives its light up to the portal plane; sidewalls and the lintel still block rays. Boundary lighting samples account for float32 rounding: a point on a doorway edge must not be incorrectly treated as behind a wall. A browser test compares floor illumination at 261 points on both sides of doorways across all seven shapes, including points 5 mm from reveals, with a tolerance of two levels out of 255.

Soft reflections of the warm room are calculated once in a 128² PMREM and shared by all rooms at low intensity. They help convey ball shape and finish properties; there are no exact mirror reflections of current doorways or objects. Contact darkening also attenuates reflected highlights so they do not brighten the pedestal base.

Through an open doorway, direct light from neighboring ceiling panels is calculated separately from soft bounced light. Source positions are transformed through the portal; ray bounds are checked against both faces of the 30 cm wall when detailed maps are filled. Wall and pedestal silhouettes from both rooms are rasterized into a separate 2048² depth atlas: up to 28 regions of 256 × 512 for four directed doorway ends. Cameras are restricted to the doorway and a small surrounding area, concentrating resolution on useful rays. The RGBA8 color atlas occupies 16 MiB, plus a depth buffer. Four PCF samples soften only the small pixel edge; depth comparison accounts for receiving-surface slope. All geometry, materials, and GPU resources are warmed up before play. The atlas updates synchronously when connections change, before the first normal frame; walking, turning, and color selection do not affect it. No engine lights or extra normal-frame passes are added. Projection results are written on the GPU into separate single-channel half-float surface maps at 2.5 cm spacing, or 1.25 cm near doorways. Seven R16F maps occupy 24 MiB. They update with depth only when connections change; a normal frame reads prepared irradiance with one bilinear sample. This removes an expensive light-source loop from the main PBR shader. Maps and their fill geometry are allocated and warmed up in advance, including initially inactive doorways. Repeated balls and bowls use a mesh matching their small lightmaps during map filling, without duplicating full geometry.

Doorway penumbrae are determined by the visible fraction of the actual square panel, including its rotation through the portal. From each receiving point, the panel is clipped by the constraints of both faces of the 30 cm wall; the remaining convex polygon's area gives smooth visibility. The transition is narrow near a jamb and widens farther away according to the geometry. The edge is not blurred with a uniform filter or split into bands from several discrete sources. Connected walls are excluded when filling the depth atlas: their central hard shadow would otherwise clip this penumbra. Other walls and pedestals retain depth-map checks. Emission strength and attenuation use the panel center with the previous balance of directional and cosine emission; this approximates an extended source's irradiance. No GPU maps or normal-frame passes are added. Small shadows from the 8 cm balls remain in local lighting.

Write regions in GPU maps are specified in physical render-target texels, independently of screen scaling. Tests compare depth and irradiance maps for a square-room loop at DPR 1 and 1.5: their contents must match. This prevents atlas-region shifts and blotchy shadows on Retina displays.

Within a threshold, both rooms use the same depth-atlas regions for light from both sides. By 60 cm from the boundary, each room's own light blends into normal local lighting. This preserves continuity at the join without restoring sharp shadows from the 25 cm grid. Colored bounce uses the same area quadrature as the room interior: full contribution within the first 0.5 m from the boundary, smoothly fading to zero at 2 m. Light does not propagate farther through a chain of doorways.

At build time, soft bounce for all **812 directed connections** between 29 doorway locations is calculated as **2D surface maps**. Game and bake geometry are created by the same function. Flat faces are grouped by plane and normal and mapped at 25 cm spacing; matching planes of open and closed walls, floors, and thresholds share coordinates. Balls and bowls have separate small maps with 8 × 6 samples that account for curved normals. Small bowls are evaluated at rim height because the diffuse occlusion model uses solid pedestal silhouettes. Thin interior socket walls receive no separate transferred light. Normal lighting and dynamic shadows are preserved. Map regions have a one-texel guard border; during baking, edge values extend into neighboring texels so filtering does not create dark bands or mix different surfaces. Repeated balls and bowls retain shared vertex and index buffers; only their additional UVs are unique.

On floors, local and transferred lightmaps use cubic B-spline sampling: smooth reconstruction from 16 neighboring texels is performed with four hardware bilinear samples. This smooths the soft lighting component; sharp direct-transfer shadows now use a separate depth atlas. Positive weights preserve nonnegative irradiance and avoid bright halos. The outermost doorway sample row lies 10 cm beyond the transition plane, in the neighboring half of the shared wall. Its lighting is calculated at its actual position rather than repeating the boundary value: both rooms reconstruct the same gradient without a small brightness jump. Visibility checks for these samples account for the full 30 cm open-doorway thickness while preserving occlusion by side reveals. Carpet textures, normals, render resolution, and ordinary shadow maps retain their previous filtering; soft-light atlas sizes are unchanged.

In each local map, R stores direct panel irradiance and GBA stores colored bounce; transfer maps use only GBA, already evaluated for the known surface normal. The receiving cosine uses the full dot product, including angled polygon walls. There are no volumetric grids in the air or six-channel textures. At build time, Node.js creates bake geometry, rasterizes surfaces, and calculates every connection. The calculation itself takes about **25 seconds in a single process** on the current machine. Results are stored without precision loss: panels use half-float, transfer values use float32, and nonzero ranges use uint32. Nonzero values are packed separately by channel; contributions below 0.0005 are removed by the same algorithm. The current level's file is about **7.17 MB**, **3.17 MB** with gzip, and **0.94 MB** with Brotli. The cache is keyed by a hash of all transitive local imports of the bake script, the generator itself, the Node.js version, and dependency files. Newly imported modules are automatically included. An edit during baking causes the hash to be checked again before publishing the result. The filename includes this revision; the loader checks it, map dimensions, and all 812 connections. Arrays are read directly from the downloaded buffer. A failed download or incompatible file leaves game entry disabled and displays a message. There are no CPU lighting-bake jobs during play.

The build writes the binary and compressed `.br` and `.gz` variants to `dist/assets/`. `npm run dev` and `npm run preview` automatically choose Brotli or gzip based on `Accept-Encoding` and send the correct `Content-Encoding`; hashed files may be cached for a year. Publishing on another static server requires equivalent serving of the prepared compressed variants, or HTTP compression of the binary; otherwise, the browser downloads the original 7.17 MB. The file already contains all lighting data for possible connections. Texture loading, shader compilation, initial shadow maps, detailed direct light, and ball reflections are still prepared on the browser GPU.

Each room has two preallocated alternating half-float 2D buffers: new light is written to the spare buffer rather than a texture the GPU may have read in the previous frame. Atlas dimensions are 128 × 128, 128 × 256, or 256 × 256; together, **14 RGBA textures occupy 3.5 MiB of GPU memory**, with the same amount used by CPU float32 working buffers. The two most recent combinations are reused without another upload. A ball action sums only nonzero texels from prepared maps; lighting and the doorway update synchronously. Closing the last doorway disables the map without uploading a texture. Walking, turning, and color selection do not change the maps. An ordinary surface reads transferred light with one 2D sample; on floors, each lightmap sample is reconstructed with four bilinear reads. Only a small region near an open doorway adds two such map reads to match illumination. A separate direct-transfer shadow atlas updates only when connections change; its calculation parameters reside in a small float texture. The main shader receives only prepared detailed irradiance. GPU texture counts and sizes remain constant during play. `profile:lighting` compares transfer enabled and disabled in ABBA order on one canvas, including the hub at 3840 × 2160; GPU results are read asynchronously.

The previous volumetric implementation was compared with surface maps in 43 views across all rooms, including recursive views, floors near entrances, and two simultaneous light contributions. Mean difference per frame is at most 0.16 levels out of 255; maximum local difference is 12. This changes the approximate interpolation model, so it is not bit-for-bit identical to the volumetric version. Running `node scripts/compare-surface-lighting.mjs --capture` saves current references to `/tmp/samewhere-lighting-reference`; running again without `--capture` compares them with the new implementation. `--image=10` saves a pair of images for visual inspection. Override the path with `--directory=/absolute/path`.

Before game entry is enabled, shader variants for the main view and portals are compiled, geometry for all seven rooms is uploaded, including closed/open walls and empty sockets, portal buffers are prepared, and all 20 initial shadow maps are calculated. Each variant is also actually rendered into a linear MSAA buffer with the same sample count as portals and into the sRGB canvas with its antialiasing: compiling GLSL alone is insufficient because drivers may defer graphics-pipeline preparation until first use. Canvas warmup is limited to a small 64 × 64 CSS-pixel region. Transferred-light fields are sampled separately, including rooms without an active doorway, and an already-used 2D map is uploaded again. GPU preparation is checked with an asynchronous fence, without a blocking readback. Static architecture for the shadow pass is merged into one geometry per room. Pedestal bodies and sockets retain their original meshes and coordinates: for front-face shadows, this avoids self-shadowing errors from rounding world coordinates in a merged buffer. Changeable walls and balls are also rendered separately. Main image geometry and socket-picking geometry remain unchanged. Static-object matrices are calculated in advance. Menu loading may take slightly longer, but a first encounter with a room needs no resource preparation. After each 64 × 64 main-canvas warmup, a complete normal room frame is restored in the same task, keeping temporary renders off screen. Once preparation finishes, another complete frame is rendered before game entry is enabled. This prevents a black flash during map application and pipeline warmup; a browser test monitors the main canvas at every preparation stage.

Contact shading reaches 20% at pedestal bases, 10% along their vertical edges and wall/floor or wall/ceiling joins, and 5% in internal vertical wall corners. All joins retain exponential falloff with a characteristic length of 10 cm (1 / CONTACT_FALLOFF) in linear light. The stronger shading is selected without accumulating multiple bands at corners; diffuse light, highlights, and ceiling emission simulating ambient light are attenuated equally. On floors, shading follows actual wall segments and pedestal silhouettes. On walls, the same profile runs along the room's internal vertical corners; projecting corners in complex rooms are not darkened. Distances to wall ends are stored in geometry and interpolated without additional maps or lighting calculations. Opening a doorway removes the band beneath the wall in the same frame, while contact continues along side jambs up to the portal plane. Pedestal bottoms extend slightly into the carpet. For bodies and bowls, the shadow map records the front face nearest the source. Body back faces lie below the floor, and single-sided bowls disappear under that culling mode: filtering the previous map could leak light at the base. The shadow depth itself is corrected, without an extra dark rim at the join. On pedestal bodies, each PCF sample is compared against the face plane's depth at the sampled texel center, rather than against the original fragment's single depth. Plane slope is calculated in the vertex shader from projected geometric tangents. This removes horizontal self-shadowing bands under side lighting while preserving actual shadows from other objects. Map sizes, sample counts, and render passes are unchanged; floor shadows retain the previous depth comparison. Diffuse light and contact shading approximate bounce and tight surface joins. All color calculations and distance fading use linear space, with conversion to sRGB at output.

Each pedestal's contact calculation is limited to its surroundings: beyond that region, the remaining exponential shading is visually negligible. This especially reduces floor work in H with its seven different silhouettes. For local sources, shadow samples and BRDF evaluation are skipped if light is outside the cone or behind the surface, where its contribution is zero. Bump normals are included before this check. Portal resolution, antialiasing, sources, and shadow-map quality are preserved. A browser test compares optimized and original calculations in 68 views across all rooms, including both views at H's four entrances. Partial shadow updates are separately compared with full rendering of the original meshes in 126 states and views, including nearby open and closed walls; the tolerance is one color level out of 255. The first frame after rearranging balls is compared with subsequent frames: lighting must not change late. `profile:hub` measures the first doorway opening and hub entry at 2565 × 1660 and 3840 × 2160; `--reference` disables the reduced calculations for comparison on the same route. `--reconnect` adds a series of openings, closures, and H entrance changes; `--full-shadows` disables partial map updates for workload comparison. The report includes updated map area, immediate lighting readiness, and the number of background jobs after play begins (which must be zero).

Pedestals are **1.20 m** tall; the distance from the center to a side of a regular polygon pedestal is **32.5 cm** (the square pedestal has a 65 × 65 cm footprint). The two pedestals in the triangular room sit symmetrically around the center on an angle bisector: X = 0, Z = ±1.95 m. Y, +, and H pedestals reproduce their room at a scale of 0.06; the longest dimension of + and H is 84 cm. Ball diameter is **8 cm**. All socket centers lie **9 cm from the nearest edge**; on regular polygons, this is 23.5 cm from the center. Sockets are closed, saucer-shaped bowls **10 cm** in diameter and **1.625 cm** deep, recessed **0.5 cm** below the pedestal surface. A short vertical wall connects the rim to the surface; total socket depth is **2.125 cm**. The material and base color of the entire socket interior, including vertical walls, match the pedestal, without additional tinting. Ball lighting and shadows are preserved. The ball's lowest point meets the bowl bottom at its center; the bottom's radius of curvature exceeds the ball radius. The pedestal exterior is one prism without a seam between upper and lower parts. Edges stay sharp, without bevels or rounding.

### Movement and recovery

Eye height is fixed at 1.65 m, player radius is 0.22 m, and walking speed is 5 m/s. Movement is split into steps no larger than 6.5 cm; after a transition, the remaining movement is transformed and continues in the new coordinate system. There is no artificial portal delay, so stepping back immediately is possible.

In A–D, walls are checked as half-planes of a convex polygon; in Y, +, and H, they are finite outline segments that account for the player's radius and open doorways. Internal corners therefore do not block adjacent branches or allow crossing voids between corridors. Pedestals use circular collision bounds based on their shape's circumscribed radius. Within a doorway's thickness, lateral collisions stop movement at the reveal without pushing the player back into the room. Interaction rays use the actual visible wall and pedestal geometry.

History is limited to 256 meaningful actions. A snapshot before each transition records a safe position inside the source room. Undo restores balls, room, pose, and selected color.

## Acceptance tests

Logic tests cover initial connections, pickup and placement, no swapping, preservation of four balls over 2,000 actions, 841 transform combinations between all 29 doorway locations, collisions, stepping back, undo, and 100 transitions without drift. Separate checks cover equal Y branches, access to every end of + and H, impassable recesses, return transitions through every end, and socket offsets from miniature edges. Room-level enumeration checks that the section leading to G is solvable and rules out solutions that always transition through A or preserve either initial connection after D.

Additional checks cover the 30 cm distance between inner wall faces, return travel, lateral collisions inside doorways, actual wall and half-wall geometry thickness, absence of outline strokes, and texture loading without external requests.

Input tests verify preservation of total movement at 30–144 frames per second, stopping without drift, and clearing accumulated movement.

Browser tests cover actual socket clicks, shared pedestal visuals, absence of a mode switch or F2 response, the complete route from A through D to G using walking and clicks, access to every socket and ball placement on each of the hub's seven pedestals, transitions between all seven shapes, and stable GPU resources after 100 cycles. WebGL frames are compared 1 mm before and after the boundary of each transition type. The whole frame is additionally checked at 0.01 mm and directly on the transition plane: both directions, rotated views, offsets toward a reveal, and reverse movement.

Color checks confirm preserved saturation nearby, smooth darkening between 48 and 68 m, and black beyond the visibility limit; direct and portal views are compared. Rays from inside each socket check all four directions and a closed bottom. Separate checks cover light counts, alignment with pedestals and shadow sources, and frame and lens dimensions. Rays into actual ceiling geometry confirm that panel centers match texture-tile centers and all four frame corners meet grid intersections.

A one-pixel checkerboard is tested on Retina displays: the portal view must retain the same contrast and match the direct view, including after window resizing. Cropped buffers are also compared with full-screen buffers during turns in both rooms.

Native pointer lock is tested through Chrome: the sum of relative events matches the final angle, compatibility `mousemove` events do not duplicate raw events, coalesced samples are counted once, and F4 restores the original view even after mouse movement during the test.

## First-version limitations

- Desktop controls only, without jumping, object physics, or saving between sessions.
- Objects can be selected only in the current room. Images inside doorways are not interactive.
- The 68 m range, 10-transition recursion limit, and 32-pass budget are fixed; distant surfaces fade smoothly to black.
- Pedestal collision uses a conservative circle rather than the exact footprint shape.
- Lighting uses PBR materials, diffuse panel area light, one approximate bounce, a shared architectural PMREM, a separate reflection map for polished balls, and cached dynamic shadows. Reflections are approximate; there is no full global-illumination ray tracing or dynamic cube cameras. Wallpaper and carpet color textures retain 1254² resolution; pedestal concrete and mineral ceiling tiles are stored as 1254² JPGs. The ceiling grid is added during loading; normal and roughness maps are calculated separately.
- State-inspection tools under `window.__samewhere` are available only in Vite development mode and are removed from production builds.

More rooms, shapes, and pedestal positions can be added through `ROOMS` configurations; ball rules and portal transforms are already separate from rendering.
